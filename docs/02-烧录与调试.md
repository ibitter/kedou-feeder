# 02 · 烧录、构建与调试

## 1. 烧录连接

飞达板上的 **H2**（4P 2.54 卧式座）就是 ISP 口：

| H2 | 信号 | 接到 USB-TTL 适配器 |
|---|---|---|
| 1 | GND | GND |
| 2 | TXD（MCU P3.1） | 适配器 **RXD** |
| 3 | RXD（MCU P3.0） | 适配器 **TXD** |
| 4 | 3V3（板载 LDO 输出） | 脱机烧录时由外部供 **3.3V**，板上电时不要接 |

注意：

- 板上电（U2 槽位 5V 供电，经 AMS1117-3.3 产生 3V3）时**不要**从 H2.4 反灌电源；两种供电方式只能选一个。
- 脚序以板上丝印为准，先量一次 H2 的 GND 与 3V3 再插线。
- 烧录时 DE（P3.5）被 2K 下拉为低电平，MAX3078E 处于接收态，不会驱动总线；RO 经 1k 电阻接 P3.6，不影响 ISP。
- 无论哪种供电，MCU 都在 **3.3V** 下运行，满足 §2.1 的校准电压要求。
- 烧录完成后必须**断电再上电**（冷启动），芯片才会进入用户程序。

## 2. STC-ISP 设置（逐项）

| 项目 | 设置 | 原因 |
|---|---|---|
| 芯片系列 | STC8H8K64U 系列 | — |
| 输入频率 | **40MHz**（使用内部 IRC） | 固件按 40MHz 计算 Timer/波特率；必须与固件 `config.h` 的 `F_CPU` 一致，并配合 §2.1 校准 |
| **下载时自动校准 IRC 频率** | **勾选** | 3.3V 供电下 IRC 会偏移，必须校准，见 §2.1 |
| 波特率 | 57600 或 115200 | 与 USB-TTL 适配器能力匹配即可 |
| **EEPROM 大小** | **≥ 512 字节**（建议 1KB） | IAP 参数区；不设会写到程序区，表现为地址/标定丢失或程序损坏 |
| P5.4 作为复位脚 | **不勾选** | P5.4 是唯一备用 IO（TP1 测试点） |
| 使能 6T/1T | 1T（默认） | 固件按 1T 计算定时器 |
| 下载后 | 冷启动 | STC-ISP 提示"请给 MCU 上电"时再上电 |

## 2.1 IRC 频率校准（3.3V 供电下必做）

**背景**：STC8H 的内部 IRC 出厂校准数据是在 **5V** 下烧录的。本板 MCU 运行在 **3.3V**（板载 LDO），
IRC 频率会偏低（典型 -1% ~ -3%）。57600 波特率的容差约 ±2%，不校准可能导致通信不稳定或无法通信。

**校准流程（STC-ISP 自动校准，固件无需任何改动）**：

1. 飞达板按**正常工作方式供电**（U2 槽位 5V → AMS1117-3.3 → 3V3，或脱机时从 H2.4 供 3.3V），
   让 MCU 运行在真实 3.3V 下；**不要用烧录器的 5V 直供 MCU**——在 5V 下校出的值回到 3.3V 运行仍会偏移。
2. STC-ISP「硬件选项」：
   - IRC 频率选择 **40MHz**（必须与固件 `config.h` 的 `F_CPU` 一致）；
   - 勾选 **「下载时自动校准 IRC 频率」**。
3. 正常下载 `firmware\build\feeder.hex`。
4. 校准值写入芯片信息区，此后**每次上电硬件自动加载**，对固件完全透明：
   `F_CPU` 保持 40000000，波特率初值、舵机 PWM 定时、延时函数全部不需要改。

**验证（首片必测，批量抽测）**：

- 方法 1：逻辑分析仪/示波器量 UART TX 位宽——57600 对应 **17.36µs/bit**，
  误差 < 1.5%（17.1 ~ 17.6µs）即合格；
- 方法 2（快速）：直接跑 `python host\feeder_cli.py --port COM7 --addr 0x05 version`，
  通信正常基本说明频率在容差内。

**异常处理**：

| 现象 | 处理 |
|---|---|
| 校准后误差仍 > 2% | 该芯片个体偏差过大；单片改 `F_CPU` 为实测值重编译，或系统统一降波特率到 38400 |
| 烧录器 5V 供电下做的校准 | 作废，按第 1 步在 3.3V 下重新校准 |
| 烧录后完全无应答 | 优先怀疑 IRC 未校准，重新勾选校准项烧录一次 |

**批量生产**：把「勾选自动校准 IRC + 目标板 3.3V 供电烧录」写进烧录 SOP，**逐片校准**
（每片芯片 IRC 偏移量不同，不可只校一片后照搬）。

## 4. 构建固件

### 4.1 Windows 一键构建

```powershell
cd firmware
.\build.ps1
```

脚本会依次尝试 `$env:SDCC_BIN` → `..\tools\SDCC\bin` → `C:\Program Files\SDCC\bin`，
并把 bin 目录前置到 `PATH`（**必须**这样，SDCC 4.5 的 `cc1` 无 `.exe` 后缀，直接绝对路径调用会报
`cannot execute 'cc1'`）。

### 4.2 Makefile

```powershell
make            # 需要 make + sdcc 在 PATH 中
make clean
```

### 4.3 常见编译问题

| 报错 | 原因 | 处理 |
|---|---|---|
| `cannot execute 'cc1'` | SDCC 的 cc1 缺 .exe 后缀 / 未加 PATH | 用 `build.ps1`，或拷贝并重命名 cc1.exe 后把 bin 加入 PATH |
| `Could not get N consecutive bytes in internal RAM for area DSEG` | STC8H 只有 128B DATA | 大缓冲必须加 `XDATA`（本项目已处理） |
| `Undefined identifier 'VENDOR_RESP_LEN'` | 宏在 .c 里定义 | 已移到 `vendor.h`，勿回退 |
| 链接后 hex 为空 | 未先建 `build/` 目录 | `build.ps1` 会自动创建 |

## 5. 首次上电自检

1. **不接舵机**，从 U2 槽位送 5V（或脱机时从 H2.4 供 3.3V）：
   - 量 5V：4.75–5.25V；`3V3`（AMS1117 输出）：3.2–3.4V；
   - 静态电流（5V 侧）< 30mA；
   - 上电瞬间 LED 不亮（未初始化）。
2. 断电，插上舵机（H1：PWM=P1.0 / 5V / GND），重新上电。
3. 发 `init`（或短按按键 SW1）：LED 常亮 = 初始化成功；舵机上电会先回 0°（约 180ms）。
4. 上电后立即用手轻推偏心轮：应能感到舵机**保持**在 0° 顶住不回弹，说明 PWM 在持续输出。

## 6. 串口调试（推荐顺序）

```powershell
# 0) 只读版本，确认通信链路
python host\feeder_cli.py --port COM7 --addr 0x05 version

# 1) 扫描/编址（新板）
python host\feeder_cli.py --port COM7 scan --program 0x05

# 2) 初始化（每次上电一次）
python host\feeder_cli.py --port COM7 --addr 0x05 init

# 3) 诊断（版本/最近结果/运行秒数/flags）
python host\feeder_cli.py --port COM7 --addr 0x05 diag

# 4) 送料并等待结果
python host\feeder_cli.py --port COM7 --addr 0x05 feed --mm 4 --wait
```

预期结果：

| 命令 | 正常输出 |
|---|---|
| `version` | `协议版本=1` |
| `init` | `status=0x00`，回显 12 字节 UUID |
| `diag` | 版本 1 / 最近结果 0x00 / 运行秒数递增 |
| `feed --wait` | 先 `status=0x00 eta=820ms`，再 `最终结果 status=0x00 (OK)` |

> ETA 公式：前进 `8ms×0.1mm + 500ms`（4mm = 820ms，2mm = 660ms），主机轮询最长等 3×ETA。
> 舵机方案的实际耗时：每 2mm 步 = `SERVO_MOVE_MS 180` + `SERVO_HOLD_MS 60`；
> 偶数步还要加 `SERVO_PEEL_MS 360` 的回程撕带，所以 4mm 实测约 840ms，ETA 只是给主机的下限估计。
> 无编码器，不需要 `cal` 标定；送料一致性由机械传动比与 `config.h` 的 SERVO_* 参数保证，改了要重新编译。

## 7. 本机 UI 行为

| 操作 | 现象 |
|---|---|
| 上电 | LED 灭；地址取存储值，未编址则 0xFF |
| 收到 0x02 且 UUID 正确 | LED 常亮 |
| Identify（0xC1） | LED 闪 3 次（300ms 亮/灭），结束后恢复初始化状态（已初始化则常亮，否则灭） |
| 送料（0x04/0x05 或按键） | LED 每 100ms 翻转一次，送料结束后恢复初始化状态 |
| 短按 SW1（>20ms，<800ms） | 手动送料 2mm |
| 长按 SW1（≥800ms） | 连续送料（每步 2mm），直到松开为止 |
| 手动送料结果 | 同样写入 0x06 的"最近结果"（0x00/0x02） |

## 8. 故障树

### 8.1 烧录失败

| 现象 | 处理 |
|---|---|
| 一直"正在检测目标单片机" | 检查 TXD/RXD 是否交叉、GND 是否共地、是否冷启动 |
| 检测到芯片但校验失败 | 降低波特率到 57600/9600；缩短杜邦线 |
| 烧录后不运行 | 确认 EEPROM ≥512B、P5.4 未设为复位脚、重新冷启动 |
| 烧录后地址丢失 | EEPROM 未分配或大小不足；重新烧录并按 §2 设置 |

### 8.2 通信无应答

1. 量 `3V3`（AMS1117 输出）与 MCU VCC（约 3.3V），以及槽位进来的 5V；
2. A/B 交换再试（接反不会损坏）；
3. 检查 DE（P3.5）静态应为 0V（接收态）；
4. 用示波器看 A/B 或 P3.6（RO）是否有波形（有波形但不应答 → 地址/UUID 不匹配）；
5. 地址 0xFF 时只有广播命令有应答：先 `scan` 再 `init`；
6. 完全无波形且无应答 → 先按 §2.1 重新校准 IRC 再烧录。

### 8.3 通信偶发丢帧

| 原因 | 处理 |
|---|---|
| 终端电阻误焊 | 飞达板不放 120Ω（BOM 里没有）；短线 57600 下多焊反而拉低摆幅，误加的要拆掉 |
| 舵机电源干扰 | 舵机 5V 就近 100µF + 0.1µF；舵机线与 A/B 分开走；地线在电源入口单点汇合 |
| 波特率偏差 | 按 §2.1 在 3.3V 下勾选「自动校准 IRC」重新烧录；确认 STC-ISP 选 40MHz |
| 多台同时上电冲突 | 本固件 0xC3 已做 0–7ms 错峰；仍冲突则逐台编址 |

### 8.4 送料异常

| 现象 | 排查 |
|---|---|
| 舵机不动 | P1.0 是否有 50Hz PWM（脉宽 0.5–2.5ms）；5V 是否到 H1；H1 插线方向 |
| 舵机抖动/中途复位 | 5V 压降过大（舵机峰值 ~0.7A，多飞达并联需独立加强供电）；就近补 100µF 电容 |
| 送料距离不准 | 开环无反馈：查拨杆是否打滑、料带是否卡滞；必要时微调 `config.h` 的 SERVO 脉宽宏后重编译 |
| 一直 COULDNT_REACH | 仅 tenths=0 时立即返回；机械卡滞会表现为运动超时无 OK |
| 撕带不足/元件没露出 | `SERVO_PEEL_MS` 偏小或撕带棘轮磨损；先确认上料时预撕 3–5 颗 |
| 退带命令无效果 | 正常——拨杆单向机构，协议退带只把舵机复位到 0° |
